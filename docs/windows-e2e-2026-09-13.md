# Windows local browser validation — 2026-09-13

## Result and scope

Three distinct Agent creations completed through the actual web UI. Their
authenticated Agent WebSockets connected 3.619–4.842 seconds after clicking
Create. Pause, resume, runtime restart, model change, direct messages, archive
and batch pause also completed. One pre-fix resume exposed a separate binary
key failure; this failed attempt is retained below rather than counted as a pass.

This supports the Windows fixes in #365, #366 and #367. It is not a guarantee
that every startup is fast: two occupied warm observation slots can queue
another start, provider authentication and network delays remain possible,
and the 120-second observation timeout does not terminate the provider.

## Measurement

Computer Use operated Chrome's visible UI: signup, computer linking, creation,
Agent settings, messages and archive confirmation. Shell access started the
local stack and read logs/configuration; it did not substitute API calls for
the Agent UI actions. Click timestamps and daemon logs share the host clock.

An independent observer sampled only the isolated Agent home every 100 ms.
Disk/runtime observations therefore have approximately 100 ms sampling
uncertainty. `runtime.status=running` is an intermediate milestone, not proof
of full readiness: the failed resume below reached it before a service crashed.
The stronger connection endpoint is the authenticated Agent WebSocket, with
MCP hello and successful real messages as additional evidence. Screenshots
confirmed UI results but their capture delay is not treated as precise latency.

These are individual samples, not load-test percentiles or a production SLA.

## Failure discovered during the real workflow

Two created successfully but failed to resume with
`message backup key has invalid length`. Read-only inspection found a 32-byte
file containing Ctrl-Z that default Windows `os.read` returned as 16 bytes.
The CRT text-mode behavior also affects newline bytes. After binary-mode I/O
and legacy CRLF handling, the same file and identity resumed and replied;
no key deletion or regeneration was used to make the test pass.

The independent fix merged as #366 while this work was in progress. #367
adopts that implementation and regression tests, and adds them to Windows CI.

## Automated checks and limits

The new starvation regressions failed before the scheduler change and pass
afterward. Deterministic provider boundaries cover creating an Agent while
another warm is blocked, pausing that blocked Agent, two startup slots,
single operation ownership across repeated ticks, queued shutdown, and a
blocked archive report that neither starves discovery nor loses shutdown
cleanup. These cover the delay mechanism without waiting 120 real seconds.

Final native Windows focused run: **309 passed, 3 skipped, 8.325 s**. It includes
the scheduler, archive lifecycle, background launch, harness launch, child
environment, keystore, reminder sync, import, control, process cleanup and
daemon configuration/catalog tests.

CI on `9080393`: Windows lifecycle on Python 3.11 and 3.12, Ubuntu full pytest
on Python 3.11 and 3.12, pre-commit/structure checks and CodeQL all passed.

The broad native Windows run was **2,811 passed, 39 failed, 38 skipped and one
pytest internal error**, 91.148 s, before aborting. The existing global
platform monkeypatch causes `cannot instantiate PosixPath on your system`;
this is an incomplete failing run, not full-suite coverage. Existing Windows
test portability failures remain outside the focused green gate. POSIX mode
bit assertions in import/reminder tests are now conditional on POSIX; their
behavior assertions still run on Windows.

Not exercised live: login/logoff autostart, other provider families, remote
runtime deployments, quota exhaustion, deliberate network/auth faults,
permission approvals, turn cancellation, compaction, irreversible deletion,
high concurrency, long soak, duplicate Create requests or recovery from
arbitrary process death. The [lifecycle inventory](windows-lifecycle-audit.md)
records the remaining ownership and retry limits. No claim is made that the
published 2.0.5 package or the user's running production installation already
contains the new scheduler.
